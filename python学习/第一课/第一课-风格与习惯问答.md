# 风格与习惯问答

> 这份文档收集"我从 C# 带过来的习惯，在 Python 里要不要改"这类问题。
> 有新问题就往下加。

---

## 你的三个习惯，先看结论

| 习惯 | 能留吗 | 说明 |
|---|---|---|
| `print (x)` 函数名后加空格 | ✅ **随便留** | 纯外观，永远不会报错 |
| `if (age > 18):` 加括号 | ✅ **随便留** | 能跑。但要分清两种用法（见下） |
| `#region` / `#endregion` | ✅ **能留！VS Code 支持** | 好消息，见第 3 节 |
| "一个大文件装所有东西" | ⚠️ **这个建议改** | 不是外观问题，是结构问题 |

**一句话**：外观习惯随你，**结构习惯要跟着 Python 走**。

---

## 1. 函数名后面的空格 `print (x)`

```python
print ("hello")     # ✅ 合法，正常运行
print("hello")      # ✅ 也是合法，PEP 8 的标准写法
```

**完全合法，永远不会报错。** Python 的语法在这里没有歧义，所以加不加空格**对程序没有任何影响**。

你可以继续留着你那套"变量后面接东西必须加空格"的视觉习惯——它确实是有效的视觉分隔。

**但要知道两件事：**

1. **PEP 8 的标准写法是不加空格。** PEP 8 是 Python 官方的代码风格指南。
2. **`black` / `ruff format` 这类自动格式化工具会把空格删掉。** 如果你以后开了"保存时自动格式化"，它会静默帮你改掉。

**建议**：留着，自己舒服最重要。等哪天你开始和别人协作、或者用黑格式化，它自然会被统一——**不值得为这个纠结**。

## 2. `if` 后面的括号

这个要分**两种用法**看，因为它们完全不是一回事：

### 用法 A：包住整个条件（冗余，不推荐）

```python
if (age > 18):
    print("成年")
```

**能跑**，但括号是多余的。Python 靠**冒号 + 缩进**划分代码块，不需要括号帮忙：

```python
if age > 18:
    print("成年")
```

### 用法 B：组合复杂条件（★ 强烈推荐，正常写法）

```python
if (age > 18) and (score > 60):
    print("录取")

if (a > 1) or (b < 2) or (c == 0):
    print("命中")
```

**这种括号在 Python 里是完全正常的，而且被鼓励**——它让运算优先级一目了然。

### 结论

| 写法 | 建议 |
|---|---|
| `if (a > 1):` 只包一个条件 | 冗余，但能跑，随你 |
| `if (a > 1) and (b < 2):` 组合条件 | **就这么写，是对的** |

所以你不是"要戒掉括号"，而是**只在需要分组的时候用**。

## 3. `#region` —— 好消息

**VS Code 的 Python 扩展支持 `#region` / `#endregion`！** 你可以继续用。

写法就是把它们变成 Python 注释：

```python
#region 玩家移动

def move_player(speed):
    print(f"以 {speed} 速度移动")

def stop_player():
    print("停下")

#endregion


#region 玩家状态

def get_hp():
    return 100

#endregion
```

保存后，`#region` 左边会出现**折叠箭头**，点一下就能把整块收起来，标题就是 `玩家移动`。

**格式要求**（这几条容易踩）：

- 必须是注释形式：`#region`，前面有 `#`
- `#` 和 `region` 之间**有没有空格都行**：`#region` 和 `# region` 都可以
- `#endregion` 同理
- **必须成对**，不配对折叠会乱

**两个注意点：**

1. 这个功能历史上出过 bug（某些嵌套场景折叠不准），不是 100% 稳，但日常够用。
2. **`#region` 是编辑器功能，不是 Python 语言功能。** PEP 8 里没有它，团队项目里可能被当成噪音。自己写没问题，交到别人手里要有心理准备。

**你"时间长了忘了指令名"的问题解决了**——就是 `#region` / `#endregion`，和 C# 一模一样，只是前面多个 `#`。

## 4. ⚠️ 真正建议改的：文件组织方式

这是你三个习惯里**唯一一个结构性**的，也是最值得改的。

**C# 的文化**：一个文件里塞很多类，用 `#region` 分区。

**Python 的文化**：**一个文件干一件事，需要就 `import`。**

```python
# player.py
def move(speed):
    ...

def stop():
    ...
```

```python
# main.py
from player import move, stop

move(5)
stop()
```

**为什么要这样：**

- Python 没有 `namespace` 这种东西，靠**模块名**（就是文件名）来区分
- 标准库和第三方库**全是这个风格**——`import os`、`import json`、`import numpy`
- 你迟早要读别人的代码，读不惯小文件会很痛苦

**`#region` 在 Python 里的正确位置**：给一个**中等大小的文件**临时分区。

**不是**：把五个功能塞进一个 500 行的文件，然后用 region 假装它们分开了。

> 判断标准很简单：**如果这个 region 里的东西能被别的地方复用，它就该是一个独立文件。**

---

## 5. Python 里"怕忘了这函数干什么"的正统解法：docstring

你说 region 的一个用途是"时间长了忘了这函数干嘛"。Python 有个**比 region 更好的东西**：

```python
def move_player(speed):
    """让玩家以 speed 的速度移动。speed 单位是像素/帧。"""
    print(f"移动 {speed}")
```

就是函数体第一行的三引号字符串，叫 **docstring**（文档字符串）。

**好处**：

- VS Code 里**鼠标悬停在这个函数名上就能看到**这段话
- 在别的地方输入 `help(move_player)` 也能打出来
- 这是 Python 的标准，所有人都认

**为什么比 region 注释好**：它**挂在函数上**。你把 region 折叠起来，标题看不见了；但 docstring 跟着函数走，无论在哪儿调用都能看到。

**建议**：每个函数都写一行 docstring，一句话就行。这是 Python 里性价比最高的习惯之一。

---

## 6. 总结

| 习惯 | 怎么办 |
|---|---|
| 函数名后加空格 | 留着，无所谓 |
| `if` 加括号 | 冗余的随你，**组合条件时该用就用** |
| `#region` | **继续用**，VS Code 支持，写法 `#region` / `#endregion` |
| 一个小文件干一件事 | **这个要适应**，是 Python 的核心文化 |
| 每个函数一行 docstring | **新习惯，强烈建议养成** |

**核心区别记一句话：**

> **C# 靠"一个文件里的分区"组织代码，Python 靠"多个文件之间的导入"组织代码。**
