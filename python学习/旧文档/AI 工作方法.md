## 为什么这份东西存在

本项目（一个非程序员设计师 + LLM）能长期跑下来，靠的不是 AI "聪明"，而是三件事：

1. **每改一次就自测一次**，用可执行的检查代替"我觉得"；
2. **报告里带证据**（命令、输出、文件:行号、通过/失败计数）；
3. **读到的结论立刻落到文档**（代码地图 / 规则文档 / 开发备忘），下一个会话不用重读。

第 1 条最关键。**自测不是礼貌，它是唯一的真相来源。**
"我觉得应该没问题"和设计师的直觉一样，都不算数 —— 只有跑出来的输出算数。

## 一、六步循环（每轮都按这个走）

### 1. 开场：读文档，然后**验证**文档
- 先读 `项目总览.md`（现状/结构/怎么跑）、`代码地图.md`（哪个模块在哪）、相关 `规则文档/0X`、以及 `开发备忘.md` 里最近那几笔。
- **然后不是"我读完了"，而是去工具里核对**：文档说"引擎在 `src/explore/engine.js` 的某函数"，就打开看；文档说"某功能未开工"，就 `grep` 确认真的没有实现。
- 文档与代码不一致时：**以代码为准**，并把这条不一致写出来（这本身就是有价值的发现）。

### 2. 定位：动手之前先搜"这件事现在是怎么做的"
- 用 `grep`/`glob` 在项目里搜相关实现，**不许假设"肯定没有第二份"**。
- 搜到第二份 → 停下来报告（《代码规定》"一个规则一个实现"），别闷头改。
- 分层记牢：**content/（内容）→ rules.js（数值）→ src/（机制）→ screens/ui（表现）**。改哪层，先想清楚。

### 3. 假设：先写下"我预计会发生什么"
- 改之前用一句话写预期（"改完这个，X 场景应该出现 Y"）。
- 这一步是为了让自测**有东西可比**；没写预期，跑出来也不知道算不算对。

### 4. 改动：最小改动，只碰拍板范围内的东西
- 不顺手优化、不重构无关部分、不"顺便"改文案。改完**自己知道改了哪几个文件**。

### 5. 自测：跑（这一节最重要，见 §四）
- **红了就先修，别往下走。** 更不许把红的写成绿的。

### 6. 报告：照模板写（见 §五）
- 有证据、有失败、有下一步；并说明这轮属于**谁的拍板**（git 提交要挂 `【拍板-*】`，见《代码规定》附 C）。

## 二、踩到报错时怎么办（最值得学的一条）

报错不是障碍，是**信息**。它把你从"我以为"踢回"实际是" —— 这个来回就是全部的秘密。

**四步，顺序不许乱：**

1. **先把报错读全**（不要只看最后一行）。最后一行往往是症状，前面几行才是原因；找有没有"文件:行号""命令:行号"。
2. **去读它说的那个地方**：打开那个文件、看那几行（连带上下 10 行）。报错说第 70 行，就真的去看第 70 行，不许凭印象。
3. **能复现就先复现，而且用最小方式复现**（例："双击闪退" → 直接 `cmd /c` 跑一遍，一次就看到真报错）。
4. **改之前先说出假设**："我认为原因是 X，证据是这一行。" 然后**一次只改一个变量**，改完再跑一次 —— 否则你不知道是谁修好的。

**三条禁令：**
- 不许**绕开**报错（换种写法让它不响，但没搞清原因）。
- 不许**猜着改**（没读到证据就动手）。
- 不许**把红的说成绿的**（没跑通就写"应该没问题"）。

**顺带一条**：报错原文要**留在报告/备忘里**，别抹掉 —— 那是这轮改动最真实的记录。

### 报错分四类（先分类，再动手）

| 类型 | 长什么样 | 该做什么 |
|---|---|---|
| ① **自带解法** | `file has not been read — read the file, then retry` | **照做**：先读，再重试**同一个**动作。别问为什么，别换动作 |
| ② **只给症状** | `TypeError: xxx is not a function` / 断言失败 / `FAIL` 行 | 去读那个文件、那段输出的上下文，拿到证据再改 |
| ③ **前置条件不足** | 没权限 / 没读过文件 / 状态不对 / 端口被占 | 先满足前置条件，再重试**同一个**动作 |
| ④ **看不懂** | 从没见过的报错 | 先**最小复现**（逼成每次都出现的情况），再报告；不许猜 |

**重试的两条规矩**
- 重试前**必须做一次新的读取**（读文件 / 读输出 / 读状态）。没有新信息的重试 = 原地撞墙。
- **同一个动作最多重试一次**。第二次还失败 → 停手，把完整上下文报告给设计师。

**铁律：绝不绕过护栏。**
不要用 shell 去改文件、不要开权限升级去硬写。护栏（比如"改文件前必须先看过它当前内容"）存在的理由就是**保护设计师的文件**；**绕过护栏比报错严重得多**。

> **真实例子（2026-09-17）**
> ```
> 编辑 Error: cannot modify "...README.md": file has not been read — read the file, then retry
> 读取
> 编辑 +6 -5 成功
> ```
> 失败原因：文件先被脚本/整篇重写动过，AI 脑中的版本已经过期 —— 护栏正是在防"拿旧印象覆盖新内容"。
> 正确的反应只有三个字：**照做（读 → 重试）**。

## 三、什么算"证据"

| 算证据 ✅ | 不算证据 ❌ |
|---|---|
| 命令 + 真实输出（贴关键几行） | "应该没问题" |
| `文件名:行号` | "我记得是这样" |
| 测试计数（跑了几项、过几项、失败 0） | "我检查过了" |
| `node --check` 通过、HTTP 状态码、打包产物存在 | "通常是这样的" |
| 你自己造的临时脚本 + 它的输出 | 用漂亮话解释原理 |

**一条硬规则**：写下任何"我记得 / 应该是 / 一般"，就先用工具复核一遍，再写进回答。
（包括对自己行为的描述 —— **自述不可靠，工具输出才可靠**。）

## 四、本项目的自测清单（照这个跑）

| 改了什么 | 跑什么 |
|---|---|
| 任何引擎/机制（`src/`） | 对应的 `test/*.test.mjs`，**逐个跑**：`node test/xxx.test.mjs`（本项目规矩：不用通配符一次性跑） |
| 涉及面广的改动 | 把 49 个测试文件都过一遍，**全绿才算完** |
| UI/界面文件（`app.js`、`ui-*.js`、`screens.js`、`item-sheet.js`、`equipment.js`） | `node --check <文件>` 做语法检查；**行为要看界面 → 交给设计师当眼睛**（见下） |
| 数值/规则改动 | 相关的 `规则文档/0X`、`rules.js` 一起看；跑数值相关测试 |
| 内容/物品/房间 | `content/*.js` 改动后跑受影响的测试；确认物品 id 段没撞 |
| 纯逻辑验证（没有现成测试） | 写个 **`_` 前缀的临时脚本**（`_sim-xxx.mjs`）直接调它，打印输入输出；**用完删掉** |
| 要给设计师看界面/demo | `node _serve.mjs` → http://127.0.0.1:8000/（临时 demo 用 `_` 前缀命名） |
| 设计师要打包件 | `node _pack.mjs` → 产出单文件（按需，不是每步都打） |

**界面/手感/动画 = AI 看不见，必须交给设计师当眼睛。** 正确做法是给他**可复述的验证步骤**：

> 打开 http://127.0.0.1:8000/ → 点「背包」→ 点某物品 → 应该看到：详情弹窗里有"拆分/合并"两行，点拆分能出数量选择。

然后请他把实际看到的告诉你。**不许写"界面已确认正常"。**

**"全绿"这句话必须有数**：几项通过、几项失败。没有数字的"测过了"，不算。

## 五、报告模板（照抄这个格式）

```
【做了什么】一句话
【改了哪些文件】逐个列出；没改的别写
【怎么验证的】
  - 命令：<原样贴>
  - 输出：<关键几行>
  - 结果：跑了 N 项 / 过 N / 失败 0（或：有几项红，红的如下）
【行为变化】玩家能看到什么不同
【最容易坏的地方】哪里最脆、现在有没有测试盯着它
【拍板归属】这轮属于 用户拍板 / AI 提案后同意 / 例行约定
【遗留 / 下一步】
【如果你要我验界面】打开哪个页面、点哪里、应看到什么
```

**三条铁律**：
- **红的写在前**，别藏在最后。
- **不要用"应该""大概""我记得"**——要么有证据，要么写"这一条我没验证"。
- **自己搞坏的东西要主动说**（例：跑脚本占了 3099 端口、临时文件忘了删）。

## 六、五个最常见的失败模式（反面清单）

| 失败模式 | 表现 | 正确做法 |
|---|---|---|
| **只读不跑** | "我看了代码，逻辑是对的" | 读是为了改，改完必须跑 |
| **猜着改** | "设计师大概想要 X" | 问一句，或给 2~3 个方案让他选 |
| **顺手优化** | 改了没拍板的地方 | 停手，只碰本次范围内 |
| **自述当证据** | "我记得这个函数返回…" | 打开文件看，或跑一下 |
| **报告没数** | "都测过了，没问题" | 报命令、报计数、报失败项 |

## 八、机制说明：为什么"先读再改"是被**强制**的

> 这一节解释环境层面的护栏。**理解它，能少踩很多坑** —— 尤其是"我明明看过这个文件，为什么不让改"。

DSH 有一层可挂载的策略：**`@deepseek-ai/dsh-fs-observation-policy`（编辑前读取的文件系统策略）**。它自己的原话：

> 要求 agent 先读取文件，文件系统工具才可覆盖或编辑它。**如果文件自读取后发生变化，它也会拒绝变更**，并提示重新读取后重试。

**它怎么拦的**

1. **三态记录**：每个文件对当前会话只有三种状态 —— **未见 / 确认缺失 / 存在于某版本**。
2. **写文件不是"覆盖"，是"比较并交换"（CAS）**：没见过 → 只允许 `createIfAbsent`（能新建，**不能覆盖**）；见过 → 要求 `replaceIfVersion`（版本必须还是我看到的那一个）；磁盘上的版本变了 → 报 **`FS_STALE_VERSION`**，拒绝。
3. **编辑没见过文件 → `FS_NOT_OBSERVED`**，工具层统一包装成：
   `cannot modify "<path>": file has not been read — read the file, then retry`

**三条必须知道的行为约束**

| 约束 | 意味着什么 |
|---|---|
| **只有 `read` 工具的读取才算"观察"**（直接调底层 fs 不算） | 改文件前必须用 read 工具读它；"我刚才在别处看过"不算数 |
| **改完之后再改同一文件 → 必须重新 read** | 版本已经变了；连续编辑同一文件时中间要再读一次 |
| **观察不跨会话保留** | 新会话想改哪个文件，就先读哪个文件 |

**所以报错不是刁难，是护栏在替设计师把关**：它防的就是"拿旧印象覆盖新内容"。
**对 AI 的要求就一句：照做（读 → 重试同一动作），绝不绕过。**

## 附：给设计师的一句话
